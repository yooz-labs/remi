# Direct TLS implementation plan (#1170)

## Context and authority

The owner accepted browser-link/download contracts, retained 10 MiB downloads,
and explicitly required HTTPS/WSS before their first direct release on
2026-10-14. Full relay tunneling follows. Existing direct signed ws:// carries
no Remi encryption. Native app source belongs to the Xcode developer.
This continues the owner-approved secure direct transport work; no new trust
grant, deployment, certificate issuance or installed trust change is authorized
by this implementation plan.

## Reuse and verified facts

- WebSocketServer owns one Bun.serve HTTP/WebSocket listener and all current
  origin, actual peer, local capability and signed-device admission routes.
- WebSocketAdapter is the shipping constructor; it must forward TLS configuration
  without duplicating routes or authentication.
- CLI and hub-to-child sockets currently use ws://127.0.0.1 with the existing
  local capability; their actual TCP loopback boundary must remain intact.
- Pairing v1 has an exact field set with no scheme; native endpoint construction
  currently hardcodes ws. A versioned secure endpoint contract/client adoption
  precedes remote TLS availability; no silent plaintext fallback is acceptable.
- Owned runtime feasibility shows HTTPS validates CA/host on both installed Buns.
  Native Bun WebSocket ca/serverName overrides do not give one qualified secure
  loopback mechanism across 1.3.11/1.4.2, so that workaround is not selected.
  Evidence: S1 artifacts/2026-10-14-direct-tunnel-acceptance/tls-loopback-probe.

## Architecture and phases

1. **TLS listener foundation** (this bounded unit): add optional PEM key/cert
   values to existing ServerConfig, pass them to the same Bun.serve, and forward
   the exact option through WebSocketAdapter. Normal TLS performs encryption;
   all existing Remi authentication/origin/peer routes are reused. Omitting TLS
   retains existing HTTP/WS. Invalid TLS configuration must fail startup; never
   catch and restart as plaintext. No second API, custom crypto, TLS trust
   bypass, global environment override, new capability or CLI config in this unit.
2. **Local routing and configuration**: wire operator-provided certificate/key
   files into daemon startup. Preserve local CLI/control/child capability access
   with a separately held loopback listener if TLS is configured, publishing
   its private port only in local process records. Public endpoint discovery
   carries its secure scheme; local fields do not leak into remote session lists.
   All startup failures/stop paths close every held listener. No remote same-host
   proxy is used to manufacture loopback trust. This phase needs exact caller
   mapping and its own review before implementation.
3. **Secure endpoint clients**: version pairing/endpoint metadata as needed,
   preserve strict older-client behavior, web WSS/HTTPS probing, and Xcode handoff
   for normal platform certificate validation. No automatic ws downgrade.
4. **Direct features**: expose accepted browser-link/download capabilities only
   on the completed secure transport with actual daemon and shipping client
   acceptance. Existing codecs/preparation stay unavailable until callers land.

## Foundation files and fixed decisions

- packages/daemon/src/server/websocket-server.ts: optional readonly tls with
  exactly readonly key:string and cert:string (PEM contents, not paths). It is
  omitted entirely from Bun.serve when absent. Keep one fetch/websocket body.
- packages/daemon/src/adapters/websocket-adapter.ts: same typed option forwarded
  through constructor/config and start. No changed adapter/connection admission.
- packages/daemon/tests/server/websocket-server-tls.test.ts: real server/adapter,
  actual temporary identity store and Ed25519 clients, actual HTTPS/WSS sockets.
  Owned short-lived CA/cert/key generated by system OpenSSL in an owned temp dir;
  never read installed secrets or commit a private key. Ensure awaited cleanup.
- .context/direct-tls-plan.md: root owned plan; worker must not edit it.

## Preregistered foundation gates

- Trusted owned CA + 127.0.0.1 IP SAN: actual HTTPS health/auth-info and signed
  WSS hello/request/response succeed on both installed Mac Buns.
- No CA: HTTPS/WSS refuses before HTTP/WS handler activity. Wrong host is tested
  through HTTPS (both runtimes enforce it); do not claim Bun1.3.11 native WSS
  hostname validation from that separate test.
- TLS never admits bare loopback without identity/capability; unknown signed
  identity remains UNKNOWN_KEY/pending; approved identity reaches hello/domain.
- Real allowed/refused origin and correct/incorrect capability controls reuse
  existing paths. TLS enables no automatic authorization.
- Plain HTTP/WS cannot use the TLS port. Invalid/mismatched/empty PEM fails
  startup; no running/plaintext fallback. TLS stop/restart and repeated start
  retain existing lifetime behavior without owned sockets/listeners/directories.
- Adapter forwarding is demonstrated by constructing and starting the real
  adapter; a server-only test is insufficient for the shipping path claim.
- Existing relevant server/adapter/auth/origin/answer populations retain all
  existing assertions; full population both Buns, root/web types zero diagnostics,
  pinned Biome 1.9.4 and diff checks. Record all failed/setup attempts honestly.
- At most full R1 and one substantial fix-only R2. Do not publish before review.

## Limits and prerequisites

This foundation does not enable a TLS daemon launch configuration or public
endpoint. It does not establish browser, native, phone, deployed, larger-payload,
link or download availability. No owner device/account/cloud/model call is
needed for local implementation. Certificate provisioning and physical-device
acceptance are later operator actions, with no automatic trust installation.

## Agent budget and judgment calls

Root owns architecture/configuration/endpoint contracts and integration. One
strong-tier bounded implementer handles the listener and its explicit checks;
one independent reviewer handles that unit. A recurring CI observer handles
already-published #1520. Maximum four concurrent agents including root, no nested
agents; reuse completed roles. Known tradeoff: standard TLS first, with local
routing/client contract in following bounded units rather than an unsafe native
WS validation override. No new certificate pinning or private CA bootstrap UX.
