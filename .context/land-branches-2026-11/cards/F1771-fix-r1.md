## Context

Round-1 findings (read the three reviews in your own words from this list):
1. Contract, Important: in `MachineStore.receive(_ state:)` the child-connection branch (`endpoint.id != parent.id`, the `.connected` case near line 2788) returns BEFORE the generation stamp in `.connected(let sessionID)` (near line 2835). On a hub-mode child reconnect `questionConnectionGenerations[session]` keeps the old generation, the previous snapshot still looks current, and because the daemon sends the re-sent `question` messages BEFORE the `question_snapshot`, replayed pending questions are posted as new. Cold launch is fine. This is the main defect; the fix must work for child (session daemon) connections as well as direct ones, without depending on `routeBySession` already holding the route or on a non-nil session id.
2. Contract, Important: (a) a session whose connection never gets an attach-time snapshot (older daemon, the query-mode attach path) is held forever and posts no local notification; this fail-closed behavior is undocumented (APNS is unaffected); (b) if a live broadcast `question_snapshot` is the first snapshot on a generation, it becomes the baseline and swallows a genuinely new question. Decide and document: fail-closed for a session with no attach-time snapshot is accepted; for (b) accept a snapshot as the baseline only if it arrives before any live `question` message that is not part of the attach replay on that generation, or record the baseline at connection time as the questions present then; choose the simplest rule that a literal test can pin and say which you chose and why.
3. Maintainability, Important: the decision of whether a snapshot is usable is split (store captures, the view's `questionNotificationInput` gates on generation equality, the policy decides). Move the gate into one pure, tested function (for example `MachineState.currentQuestionSnapshot(for:)` returning the snapshot only when generations match, or pass both generation values to the policy); the view becomes a thin mapper.
4. Maintainability, Important: `MachineQuestionConnectionSnapshot` (RemiKit) and `RemiQuestionNotificationPolicy.ConnectionSnapshot` are identical; use the store type in the policy signature (RemiUI already imports RemiKit) and delete the duplicate; do not make the two new `MachineState` dictionaries public if only an in-package accessor is needed.
5. Maintainability and Contract, Important/Minor: `questionConnectionGenerations`, `questionConnectionSnapshots` (store) and the policy's `connectionGenerationBySession` are not pruned when a session is killed; clear both store dictionaries in the same block that clears the session's other per-session state (near the kill path, `routeBySession[killedKey] = nil` and siblings), and have the policy drop entries for sessions absent from its input; tests for both.
6. Verification and Maintainability, Important: the store half is covered only by `contains(...)` source-text checks. Replace them with behavior tests that drive `store.receive(...)` the way `SessionAddressingTests` does (first snapshot kept per generation, a second same-generation snapshot ignored, a new generation replaces, a stale-generation snapshot is not current, a CHILD-endpoint reconnect `store.receive(.connected(sessionId: nil), from: child, generation: G2)` then `.question` then `.questionSnapshot` shows no usable snapshot until the new snapshot arrives, session removal clears the state). Keep at most one coarse source guard for the view and strengthen it: slice `questionNotificationInput` and the onChange block (range-based, `#require`) and assert the call uses `update.questionIDsToPost`, `update.questionIDsToRemove` and stores `questionNotificationPolicyState = update.state`.
7. Verification, Important + Minor: add literal table rows for the held-then-snapshot sequence (questions present, no snapshot: post none and known none; then the snapshot arrives: post none), a two-session or two-machine row, a vanished-session row, and a reconnect whose snapshot omits previously known ids while a genuinely new id appears; give every row a name passed as the `#expect` comment; add one chained test (update, remove q, re-add q, each result's state feeding the next).
8. Verification, Important: the card required one revert check per behavior and only one was run. Run and record in the evidence folder `/Volumes/S1/yooz/remi/artifacts/land-branches-2026-11/F1771/r2/` one isolated mutation log each (apply, run the focused tests, quote the failing line, restore): the old inline baseline in the view; `isNewConnection` always false in the policy; the policy ignoring `snapshot.questionIDs`; the policy never posting; the store overwriting the snapshot on every call; the child-branch reset removed.
