## Context

Findings (contract C, verification V, maintainability M; all high confidence unless stated; the reviewers reproduced 1 to 4 by running the policy):
1. C1, V1, M1 Important: the hook `SessionEnd` is mapped to the policy's terminal `session-end` event (`hook-bridge-setup.ts` near line 1055), which sets `ended=true` forever (`awake-policy.ts` near 105 and 165). `SessionEnd` also fires on `/clear` and `/resume` with the PTY and daemon alive, so the hold is lost for the daemon's life. Reserve the terminal event for `AwakeSession.dispose()` (PTY exit, registry close, cleanup); map the hook `SessionEnd` to turn-close plus status idle (the bridge's `handleSessionEnd` already sets idle), and a later turn-open, busy status or activity must hold again.
2. C2, M2 Moderate (and part of V4): `AwakeHolder` installs `process.on('SIGINT')` and `process.on('SIGTERM')` listeners whose handler disposes the whole session and never exits; wrapper mode forwards SIGINT to the PTY and keeps running, and a SIGTERM listener removes the default terminate action in the window before `cli.ts` registers its own. Remove the SIGINT and SIGTERM listeners and the `onTermination` option; keep the synchronous `exit` release, `-w <pid>` and the `cli.ts` cleanup. The original card's design item 3 asked for the handlers; it was wrong for wrapper mode (owner-level design note: process death is covered by `-w`).
3. C3 Moderate: when the stuck bound fires, the policy releases but leaves `turnOpen=true` and the busy status, so any later PTY output re-arms the hold. On `stuckExpired`, clear `turnOpen` and reset the status to idle in the same step; only a fresh turn-open or busy status may hold again.
4. C4, M3 Moderate: a pending question sets status `waiting`, a busy status, so `statusActive` keeps the hold past `question_hold_minutes` while any activity arrives. Treat `waiting` as covered by the question while `questionCount > 0` (`statusActive = hasBusyStatus && fresh && !(status === 'waiting' && questionCount > 0)`), so the cap really bounds it; the "question cap reached" log must be true. Also: a question replaced at the same count restarts the cap clock (reviewers' minor item): decide in favor of restarting only when the count goes 0 to nonzero, and test it. Add a cross-field check in `validateAwake` only if one is still needed after this change, else none.
5. C5, V4 Minor/Moderate (medium confidence): any caffeinate exit with a nonzero code or signal, any failed replacement spawn, and any transient spawn error latch `failed` forever with a misleading log. Latch only for `ENOENT` or `EACCES` on spawn (word the log by cause). For an unexpected exit while the policy still wants a hold, re-spawn with a bounded attempt count (3) and a small backoff, log once, and then stop trying until the next hold transition; an unexpected clean exit 0 is handled the same way. Add tests (kill the real caffeinate, then new work holds again; a non-darwin platform returns false without spawning).
6. V2, M5 Important: `awake-wiring.test.ts` builds its own `SessionRegistry` callback and so cannot fail on the `cli.ts` glue: removing every `noteWorkEvent` activity call, the `StopFailure` turn-close or `AwakeSession.questionsChanged` left all 18 tests green. Move the registry-to-awake glue and the creation condition (not serve mode, darwin, `level1`) out of `cli.ts` into a small production module (for example `packages/daemon/src/power/awake-wiring.ts`) that `cli.ts` and the test both import; keep the `harness/` import boundaries (`tests/harness/harness-boundary.test.ts` must pass unchanged; do not add imports to `harness/codex/` or `claude-session.ts` beyond what exists). Add tests with a real `SessionRegistry`: a question alone (no `UserPromptSubmit`) holds and its removal releases after grace; an Escape case (`UserPromptSubmit`, no `Stop`, short config, advance past the stuck bound, release plus one warning); the Claude PTY output wrapper emits an `activity` work event; the Codex notification and PTY paths emit one (assert through `subscribeWorkEvents`, constructing the real session objects the existing suites already construct, or narrow the test title to what runs); `StopFailure` turn-close; `SessionEnd` with reason `clear` then `UserPromptSubmit` holds again (`holder.starts === 2`). Record a revert log per wiring mutation (the same mutations the verification reviewer used: remove each `noteWorkEvent` activity call, remove the `StopFailure` turn-close, make `questionsChanged` a no-op, remove the dispose in cleanup) showing a test fails.
7. V3 Moderate: add real-process tests in `awake-holder.test.ts`: (a) `renew()` with a real caffeinate: poll `pmset -g assertions` and assert the target pid is never absent between the new holder appearing and the old pid exiting, and the old pid is gone afterwards; a mutation log for kill-before-spawn; (b) the `exit` handler releases the assertion when the owning process exits normally (bind `-w` to a separate long-lived child pid so that only the handler can release it); (c) a SIGINT delivered to a holder-owning process that handles it does not release the hold. Optionally give `AwakeSession` an injectable clock so a renew-through-timer test needs no real wait; no wall-clock assertion longer than a few seconds.
8. V5 Moderate (medium confidence): the 178 failures and 31 errors of the full local daemon run are not shown unrelated, and the failing set includes `harness/claude-session.test.ts` (12), `integration/browser-link-composition` (5), `file-download-cli` (12), `relay-file-discovery` (2), `direct-tls-local-routing` (1), `cli/daemon-manager-command` (1). Rerun exactly those files with `TMPDIR=/private/tmp` (the L09 evidence shows that clears the `/var` versus `/private/var` class) at the base `b4aa770a` (a scratch worktree under `/Volumes/S1/worktrees/remi/`, removed afterwards with `git worktree remove` without force) and at the final head; compare failing test names and record both lists in the evidence folder.
