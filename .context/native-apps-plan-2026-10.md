# Native apps and the Xcode handoff: scope

Written 2026-10-06. Status: proposal; the owner decisions it needs are listed last.

## Goal

A native SwiftUI Mac app that works like Conductor (many agent sessions, each in its own worktree, across several machines, in one window), and a native iPhone app, both designed to the standard of Apple's own apps.
Most of the Swift is to be written by the agents inside Xcode (Claude and Codex in Xcode's agentic coding), with every change reviewed and gated in this repo as today.

This is strategy decision D7 (`strategy-2026-10.md`): native apps "built in Xcode, UX on par with OpenAI's apps and Conductor", sequenced after the protocol freeze.
The competitive review names Conductor "the UX bar for a native Mac app"; remi's own multi-machine row there reads "Yes, weakly (no machine object, socket-per-session)".

## Proposed architecture

1. **The apps are clients of hubs; they never spawn agents.**
   The Mac app stays sandboxed and asks a hub to start a session (`create_session_request`), as the phone does.
   The Mac it runs on is one more machine in the list, reached over loopback.
   One code path then serves the local machine, a second Mac over a direct link, and any machine over the relay, and the sandbox keeps App Store distribution open.
   Conductor's worktree-per-session model becomes a daemon feature (Phase 0.3), not an app feature.
2. **One Swift package, `RemiKit`, holds everything that is not UI**: protocol models, identity and auth, the connection, relay v2, push codec, and the multi-machine store.
   The Mac app, the iPhone app, the NSE and later the Watch app are thin targets over it.
   A package needs no project-file edits when files are added, which suits agents, and its tests run with `swift test` as well as in Xcode.
3. **Freeze the protocol before the UI** (D7).
   Everything a native client renders comes from the wire, so each gap below is closed in TypeScript first, with golden fixtures, and the Swift side conforms to the fixtures.
4. **Design language: current Apple design (Liquid Glass) on current OS versions**, with a written design brief (Phase 0.4) so two agents in two tools produce one product.

### 0.3 Protocol freeze

Each item: protocol types in `packages/shared`, daemon support, golden fixtures, and an ADR where it is a decision.

- [ ] **Machine object.** A stable machine id, a display name, platform, remi version, harnesses and capabilities, on `hello_ack` and the hub census; every session list entry names its machine. Set or remove `daemonHost`. On the relay the id is derived from the machine key, so the two cannot disagree.
- [ ] **Decision object.** Freeze `Question` as the Decision: decide which of `localRender`, `answerPath`, `resolvedBy` go on the wire, and add the strategy's `sandbox` and `trust` kinds or drop them from the strategy.
- [ ] **Workspaces (the Conductor model).** `create_session_request` gains a workspace: repository path, and optionally a new worktree with branch name and base. The hub creates the worktree, starts the session in it, and reports it on the session. A request for the hub's recent repositories lets the app offer "new session in repo X on machine Y".
- [ ] **Workspace inspection.** Git status and diff for a session's worktree, and the file frames of #1170, so the app can show what an agent changed. Can follow the first app release.
- [ ] **Versioning.** A protocol version and capability list on `hello_ack`, so a newer app can talk to an older hub and say what is missing instead of failing.
- [ ] **Fixture coverage.** A golden fixture for every message type a native client sends or reads, relay v2 messages included.
- Profiles (#1157) and the image tunnel (#1170) add `create_session_request.profile` and upload frames; decide whether they join the freeze or extend it later.

## Phase X: in Xcode

Each phase is an issue with acceptance criteria; each lands as a PR here and passes the same gates and review.

| Phase | Scope | Done when |
|---|---|---|
| X1 `RemiKit` core | Codable protocol models; Ed25519 identity in the Keychain and the `auth_challenge` exchange, including the #873 "approve this device on the Mac" state; the WebSocket connection with reconnect; a store holding many machines at once | Every golden fixture round-trips; a test connects to a real hub started from source and lists its sessions |
| X2 relay and native R6 | Port of `packages/shared/src/relay` (handshake, channel, pairing, push); answer signing from the shared Keychain; NSE actions on secure cards; a short-lived background channel opened from a notification action | All relay v2 vectors pass in Swift; a TypeScript hub accepts a Swift-signed native answer; the owner's signed-device gate |
| X3 Mac app | Three columns: machines and repositories, their sessions, the session. Transcript with structured agent output, question cards inline, composer, new-session sheet (machine, repository, worktree, harness, model), menu bar extra kept, native notifications | Replaces the WebView window for daily use on two machines |
| X4 iPhone app | Sessions grouped by machine, the session view, question cards, pairing, secure push with lock-screen actions | Parity with the Capacitor app; Capacitor iOS retired (owner decision 5) |
| X5 workspace depth | Diff view, file preview (#1170), a terminal view over the raw PTY stream, pull request flow | Owner can review an agent's change on the phone |
| X6 extras | Live Activities for a running turn, Watch answers (#665), widgets, App Intents | Per item |

X1 and X2 are the best first tasks for Xcode's agents: they are precisely specified, and the fixtures and vectors decide whether they are right.
X3 and X4 are where Xcode's previews and simulators pay off.

## How the work splits

- **Xcode's agents:** Swift, SwiftUI, previews, Swift tests, simulator runs. One issue per session, briefed from this document and the issue.
- **Here:** the TypeScript side of every protocol change, review of every Swift PR (including a security review of the crypto port), the full gates, and releases.
- The same branch and PR flow as today: a branch per issue off the epic or develop, pins before fixes, atomic commits.

## Owner decisions

1. **Release 0.7.16 now?** It carries the failure-alert fixes (#1153, #1226), the removal of the local judge (#1125: remi no longer starts the local engine; the one running since October 4 has to be stopped by hand), Codex support, and #873, which no longer trusts a new client key automatically: every phone and browser must be approved once with `remi authorize` on the Mac.
2. **Minimum OS for the native apps:** the current major versions (Liquid Glass, newest SwiftUI) or older ones for reach.
3. **Mac app distribution:** App Store (the sandboxed hub client proposed here) or Developer ID.
4. **Project structure:** retire xcodegen for a checked-in project with synchronized folders.
5. **When to retire the Capacitor iOS app:** at X4 parity, or keep it as a fallback for a release.
6. **Worktree location and cleanup** for hub-created workspaces (inside the repository, or under `~/.remi`), and whether the hub may delete a worktree when its session is closed.
