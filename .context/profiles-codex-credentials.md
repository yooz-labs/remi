# Codex credential sources for profiles

This note characterizes Codex 0.167.0 source at `rust-v0.167.0`, commit `086ccc833bc9cf01024ad2dd6af7dbd421b6bf9a`. Placeholder status runs used fresh empty scratch homes. They did not use a real credential or keyring.

## 1. Environment variables that supply or select credentials

### Codex account login

- `CODEX_HOME` selects the Codex state directory. Codex reads the selected auth store there, including `auth.json` for `file`; if `CODEX_HOME` is unset, `find_codex_home` uses the platform home directory plus `.codex`. A profile must set `CODEX_HOME` to its own directory. `[src: codex-rs/utils/home-dir/src/lib.rs:5-18; codex-rs/login/src/auth/storage.rs:51-57 @ rust-v0.167.0]`
- `CODEX_API_KEY` supplies API-key auth when the caller enables that source and the login policy allows API keys. The loader checks it before any other auth method and returns it immediately. At this tag, the flag is enabled by the MCP auth paths, plugin auth, `codex exec` and exec worktree, exec-server local and remote auth, the CLI model-catalog path, login-policy validation, app-server in-process bootstrap when its caller flag is true, and doctor network checks. It is false in the interactive TUI setup and onboarding loaders, the standalone app-server auth manager, and the app-server-client test setups. A scrub is required for `codex exec` and exec-server. It is defense in depth for the TUI that remi launches through `remi codex` and for remi's app-server path, whose main auth manager passes false. `codex login status` also passes false, so this source does not affect that command. `[src: codex-rs/login/src/auth/manager.rs:1017-1041,1572-1593,1416-1424; codex-rs/cli/src/mcp_cmd.rs:638-643,690-695; codex-rs/cli/src/plugin_cmd.rs:788-790; codex-rs/exec/src/lib.rs:752; codex-rs/exec/src/worktree.rs:48; codex-rs/exec-server-cli/src/config.rs:149-181; codex-rs/cli/src/main.rs:2191; codex-rs/app-server/src/in_process_bootstrap.rs:147-159; codex-rs/cli/src/doctor.rs:412-415; codex-rs/cli/src/doctor/network.rs:51-56; codex-rs/tui/src/lib.rs:744-756,1119-1126,1461-1465; codex-rs/app-server/src/lib.rs:598-604; codex-rs/app-server-client/src/lib.rs:960-970,2194-2204; codex-rs/cli/src/login.rs:488-507 @ rust-v0.167.0]`
- `CODEX_ACCESS_TOKEN` supplies an access token. When the allowed login method permits it, Codex checks it after ephemeral auth and before the persistent file/keyring store, then classifies it as an agent identity token or personal access token. `[src: codex-rs/login/src/auth/manager.rs:1017-1041,1595-1701 @ rust-v0.167.0]`
- `OPENAI_FEDERATION_RULE_ID` or `OPENAI_IDENTITY_TOKEN_FILE` selects workload identity. Either marker selects that mode; incomplete settings fail validation instead of falling back. `OPENAI_WORKLOAD_IDENTITY_CONTEXT` supplies optional context but is not itself a selection marker. `[src: codex-rs/protocol/src/shell_environment.rs:10-12; codex-rs/login/src/auth/workload_identity.rs:123-168,246-264 @ rust-v0.167.0]`
- `OPENAI_API_KEY` is read for API-key entry prefill, the realtime API fallback, and the OpenAI credential broker. It is not read by `AuthManager::load_auth` as a Codex account login source, and `codex login status` does not use it to select a stored login. `[src: codex-rs/login/src/auth/manager.rs:1017-1026; codex-rs/tui/src/onboarding/auth.rs:945-957; codex-rs/core/src/realtime_conversation.rs:1982-1996; codex-rs/network-proxy/src/credential_broker/providers/openai.rs:12-32 @ rust-v0.167.0]`
- `CODEX_AUTHAPI_BASE_URL` changes the `whoami` endpoint used to hydrate a personal access token. `CODEX_REFRESH_TOKEN_URL_OVERRIDE` overrides token refresh routing; `CODEX_REVOKE_TOKEN_URL_OVERRIDE` overrides revocation routing, or falls back to a URL derived from the refresh override; `CODEX_APP_SERVER_LOGIN_CLIENT_ID` overrides the OAuth client id. These change auth endpoints or client identity, not which stored credential wins. `[src: codex-rs/login/src/auth/personal_access_token.rs:11-13,53-64; codex-rs/login/src/auth/manager.rs:230-234,1862-1878; codex-rs/login/src/auth/revoke.rs:134-145 @ rust-v0.167.0]`

`HOME` is held at the scratch directory for every placeholder run. Codex source calls `dirs::home_dir()` only as the fallback for `CODEX_HOME`; the tests set `CODEX_HOME` explicitly, so no home-directory credential store is consulted. `[src: codex-rs/utils/home-dir/src/lib.rs:5-18 @ rust-v0.167.0]`

### Selected model-provider credentials

- A configured `model_providers.<id>.env_key` names an arbitrary environment variable that Codex reads as that provider's API key. Provider auth checks this environment key before the provider's inline experimental bearer token and before falling back to Codex account auth. `env_http_headers` can also name arbitrary variables whose values are sent as provider headers. These names depend on the selected config, so source does not provide a finite global list. `[src: codex-rs/model-provider-info/src/lib.rs:167-176,200-207,218-224,519-536; codex-rs/model-provider/src/auth.rs:284-309,379-390 @ rust-v0.167.0]`
- `OPENAI_BASE_URL` is context for the OpenAI credential broker when it binds an `OPENAI_API_KEY` to a host. It can change the credential destination, not the selected Codex account. `[src: codex-rs/network-proxy/src/credential_broker/providers/openai.rs:12-32,68-86 @ rust-v0.167.0]`
- The selected Bedrock provider can use `AWS_BEARER_TOKEN_BEDROCK`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY`. Bedrock source selection prefers configured command auth, credential export, configured profile, managed credentials, environment bearer token, environment access-key pair, then the AWS SDK chain. Codex's network proxy handles `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_SESSION_TOKEN`, and `AWS_SECURITY_TOKEN` while selecting and masking local AWS credentials; Codex also preserves `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`, and `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` for its background command. Whether the AWS SDK itself reads those variables or additional environment variables is not settled by Codex source. `[src: codex-rs/model-provider/src/amazon_bedrock/auth.rs:29-90,139-158,185-193; codex-rs/network-proxy/src/aws_sigv4.rs:266-275,293-296,317-336; codex-rs/app-server-daemon/src/background_command.rs:48-76 @ rust-v0.167.0]`
- `GOOGLE_APPLICATION_CREDENTIALS` selects a Google credential file in the default GCP auth path. An explicit provider `credential_file` takes precedence. These provider credentials do not select the Codex account shown by `codex login status`. `[src: codex-rs/model-provider-info/src/lib.rs:183-191; codex-rs/app-server/src/request_processors/account_processor/gcp_setup.rs:157-168 @ rust-v0.167.0]`

The run matrix set each of these 23 fixed variables one at a time: `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `OPENAI_API_KEY`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT`, `CODEX_AUTHAPI_BASE_URL`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE`, `CODEX_REVOKE_TOKEN_URL_OVERRIDE`, `CODEX_APP_SERVER_LOGIN_CLIENT_ID`, `OPENAI_BASE_URL`, `AWS_BEARER_TOKEN_BEDROCK`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`, and `GOOGLE_APPLICATION_CREDENTIALS`. `HOME` and `CODEX_HOME` were bound to the fresh scratch paths in every run, as required to keep the run isolated. The dynamic provider `env_key` and `env_http_headers` variables were not added to the test config because each config was required to contain only the store setting. All 72 calls (three no-variable baselines plus 23 variables for each of three stores) exited 1. The baseline and most variable cases printed `Not logged in`; the placeholder access token and partial workload identity cases printed errors. No output matched the email pattern or signed-in detector. `[evidence: /Volumes/S1/yooz/remi/artifacts/profiles-epic-2026-11/P1C/r2/placeholder-runs.txt]`

## 2. Default store and `auto`

`AuthCredentialsStoreMode` marks `File` as its default, and configuration resolves an absent setting through that default without an OS-specific branch. The default is therefore `file` on macOS and Linux. On load, `auto` reads keyring first, then reads file if the keyring has no entry or errors. On save, it writes to keyring first and falls back to file on error. This behavior has no OS-specific branch, while actual keyring availability was not measured here. A managed `cli_auth_credentials_store` requirement overrides the config value; a 0.0.0 local build maps configured `keyring` and `auto` to `file`. The default-store characterization assumes no managed requirements layer and the default `SecretAuthStorage` state, which is disabled by default on macOS and Linux and selects the `Direct` keyring backend there. Managed-requirements-file presence for the default-store runs was not checked. `[src: codex-rs/config/src/types.rs:135-148,167-185; codex-rs/core/src/config/mod.rs:288-299,4582-4590; codex-rs/core/src/config/auth_keyring.rs:70-78,110-117; codex-rs/features/src/lib.rs:1161-1165; codex-rs/login/src/auth/storage.rs:593-640 @ rust-v0.167.0]`

## 3. Keyring names and separation

With the `Direct` backend, the CLI auth store uses keyring service `Codex Auth` and account `cli|` plus the first 16 hexadecimal characters of SHA-256 over canonical `CODEX_HOME`. With the `Secrets` backend, the auth payload is in an encrypted secrets file under `CODEX_HOME`; its passphrase uses service `codex` and account `secrets|` plus the first 16 hexadecimal characters of SHA-256 over canonical `CODEX_HOME` for the `CodexAuth` namespace. Both backends therefore separate distinct canonical homes; symlink aliases resolving to the same path share an account. The answers assume no managed requirements layer and the default `SecretAuthStorage` state (disabled on macOS and Linux, selecting `Direct`); a managed feature requirement can select `Secrets`. `[src: codex-rs/login/src/auth/storage.rs:302-320,343-380,416-445,460-476; codex-rs/secrets/src/lib.rs:23,182-207; codex-rs/secrets/src/local.rs:176-208; codex-rs/config/src/types.rs:167-185; codex-rs/core/src/config/auth_keyring.rs:13-18,71-78,97-117; codex-rs/features/src/lib.rs:1161-1165 @ rust-v0.167.0]`

## 4. `codex login status` output

- No auth: stderr `Not logged in`, exit 1.
- ChatGPT auth: stderr `Logged in using ChatGPT`, exit 0.
- API-key auth: stderr `API key configured - <formatted key>`, then `Authentication is checked when you send a request.`, exit 0. For a key longer than 13 characters the formatter emits its first 8 and last 5 characters around `***`; shorter values become `***`.
- Agent-identity access token: stderr `Logged in using access token`, exit 0.
- Personal access token: stderr `Logged in using personal access token`, exit 0.
- Workload identity: stderr `Logged in using workload identity`, exit 0.
- Bedrock API key: stderr `Logged in using Amazon Bedrock API key`, exit 0.
- Bedrock AWS access keys: stderr `Logged in using Amazon Bedrock AWS access keys`, exit 0.

Status disables only `CODEX_API_KEY` auth. It still honors `CODEX_ACCESS_TOKEN` and the workload-identity selectors `OPENAI_FEDERATION_RULE_ID` and `OPENAI_IDENTITY_TOKEN_FILE`; either can make it print an exit-0 signed-in line from the environment with no stored login. The normal status format strings include no email, account id, or workspace-name fields. Error formats interpolate lower-layer text, so source alone does not establish that every possible error string is free of identifiers. The logged-in cases above are source characterizations only; no real login was read or created. `[src: codex-rs/cli/src/login.rs:488-553,697-704; codex-rs/login/src/auth/manager.rs:1017-1041,1595-1701; codex-rs/login/src/auth/workload_identity.rs:123-168,246-264 @ rust-v0.167.0]`

## 5. App-server control socket path length

The advertised control socket is `$CODEX_HOME/app-server-control/app-server-control.sock`. On Unix, Codex binds the physical socket at `/private/tmp/codex-daemon-<uid>/<sha256-of-advertised-path>` on macOS (the root is the canonicalized `/tmp`, which resolves to `/private/tmp`) and leaves a symlink at the advertised path. If connecting to the advertised path fails with `InvalidInput` because it exceeds `sun_path`, the client canonicalizes the symlink and retries the short target. The tagged source test creates two distinct homes under a 120-character parent, starts both sockets, and connects through both long paths; that test was read, not run. The source states no numeric `CODEX_HOME` maximum; ordinary filesystem path limits still apply. `[src: codex-rs/app-server-transport/src/transport/mod.rs:56-80; codex-rs/app-server-daemon/src/lib.rs:351-359; codex-rs/app-server-transport/src/transport/unix_socket.rs:69-145,353-368; codex-rs/uds/src/daemon_directory.rs:13-18; codex-rs/uds/src/lib.rs:166-173; codex-rs/app-server-transport/src/transport/unix_socket_tests.rs:63-104 @ rust-v0.167.0]`

## Consequences for P1B

For Codex account and selected-provider credentials, set `CODEX_HOME` to the selected profile and scrub these 23 fixed environment-variable names from the launched process: `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `OPENAI_API_KEY`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT`, `CODEX_AUTHAPI_BASE_URL`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE`, `CODEX_REVOKE_TOKEN_URL_OVERRIDE`, `CODEX_APP_SERVER_LOGIN_CLIENT_ID`, `OPENAI_BASE_URL`, `AWS_BEARER_TOKEN_BEDROCK`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`, and `GOOGLE_APPLICATION_CREDENTIALS`.

Configured provider `env_key` and `env_http_headers` names are arbitrary and cannot be enumerated from Codex source. Whether P1B refuses profiles that configure them or dynamically scrubs their names is a P1B policy decision; this note does not decide it. P1B must apply its environment scrub before running `codex login status`, because that command honors `CODEX_ACCESS_TOKEN` and workload-identity selectors and can report an environment-only logged-in state.

Under the assumption of no managed requirements layer and the default `SecretAuthStorage` state, the default backend is `Direct` on macOS and Linux. Separation holds for both `Direct` and `Secrets` because each keyring account hashes canonical `CODEX_HOME`; with `Secrets`, the encrypted auth file is also under that home and its passphrase is stored under service `codex` and account `secrets|<hash>`. The result is **separated**, so J11 permits `keyring` and `auto` from the account-separation finding. `[src: codex-rs/login/src/auth/storage.rs:302-320,416-445; codex-rs/secrets/src/lib.rs:23,182-207; codex-rs/config/src/types.rs:167-185; codex-rs/core/src/config/auth_keyring.rs:13-18,71-78,110-117; codex-rs/features/src/lib.rs:1161-1165 @ rust-v0.167.0]`
