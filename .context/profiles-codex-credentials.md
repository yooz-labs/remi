# Codex credential sources for profiles

This note characterizes Codex 0.167.0 source at `rust-v0.167.0`, commit `086ccc833bc9cf01024ad2dd6af7dbd421b6bf9a`. Placeholder status runs used fresh empty scratch homes. They did not use a real credential or keyring.

## 1. Environment variables that supply or select credentials

### Codex account login

- `CODEX_HOME` selects the Codex state directory. Codex reads the selected auth store there, including `auth.json` for `file`; if `CODEX_HOME` is unset, `find_codex_home` uses the platform home directory plus `.codex`. A profile must set `CODEX_HOME` to its own directory. `[src: codex-rs/utils/home-dir/src/lib.rs:5-18; codex-rs/login/src/auth/storage.rs:51-57 @ rust-v0.167.0]`
- `CODEX_API_KEY` supplies API-key auth when the caller enables that source and the login policy allows API keys. The loader checks it before any other auth method and returns it immediately. MCP and plugin paths enable it. `codex login status` passes `false`, so this source does not affect that command. `[src: codex-rs/login/src/auth/manager.rs:1017-1041,1572-1593; codex-rs/cli/src/mcp_cmd.rs:638-643,690-695; codex-rs/cli/src/plugin_cmd.rs:788-790; codex-rs/cli/src/login.rs:488-507 @ rust-v0.167.0]`
- `CODEX_ACCESS_TOKEN` supplies an access token. When the allowed login method permits it, Codex checks it after ephemeral auth and before the persistent file/keyring store, then classifies it as an agent identity token or personal access token. `[src: codex-rs/login/src/auth/manager.rs:1017-1041,1595-1701 @ rust-v0.167.0]`
- `OPENAI_FEDERATION_RULE_ID` or `OPENAI_IDENTITY_TOKEN_FILE` selects workload identity. Either marker selects that mode; incomplete settings fail validation instead of falling back. `OPENAI_WORKLOAD_IDENTITY_CONTEXT` supplies optional context but is not itself a selection marker. `[src: codex-rs/protocol/src/shell_environment.rs:10-12; codex-rs/login/src/auth/workload_identity.rs:123-168,246-264 @ rust-v0.167.0]`
- `OPENAI_API_KEY` is read for API-key entry prefill, the realtime API fallback, and the OpenAI credential broker. It is not read by `AuthManager::load_auth` as a Codex account login source, and `codex login status` does not use it to select a stored login. `[src: codex-rs/login/src/auth/manager.rs:1017-1026; codex-rs/tui/src/onboarding/auth.rs:945-957; codex-rs/core/src/realtime_conversation.rs:1982-1996; codex-rs/network-proxy/src/credential_broker/providers/openai.rs:12-32 @ rust-v0.167.0]`
- `CODEX_AUTHAPI_BASE_URL` changes the `whoami` endpoint used to hydrate a personal access token. `CODEX_REFRESH_TOKEN_URL_OVERRIDE` overrides token refresh routing; `CODEX_REVOKE_TOKEN_URL_OVERRIDE` overrides revocation routing, or falls back to a URL derived from the refresh override; `CODEX_APP_SERVER_LOGIN_CLIENT_ID` overrides the OAuth client id. These change auth endpoints or client identity, not which stored credential wins. `[src: codex-rs/login/src/auth/personal_access_token.rs:11-13,53-64; codex-rs/login/src/auth/manager.rs:230-234,1862-1878; codex-rs/login/src/auth/revoke.rs:134-145 @ rust-v0.167.0]`

`HOME` is held at the scratch directory for every placeholder run. Codex source calls `dirs::home_dir()` only as the fallback for `CODEX_HOME`; the tests set `CODEX_HOME` explicitly, so no home-directory credential store is consulted. `[src: codex-rs/utils/home-dir/src/lib.rs:5-18 @ rust-v0.167.0]`

### Selected model-provider credentials

- A configured `model_providers.<id>.env_key` names an arbitrary environment variable that Codex reads as that provider's API key. Provider auth checks this environment key before the provider's inline experimental bearer token and before falling back to Codex account auth. `env_http_headers` can also name arbitrary variables whose values are sent as provider headers. These names depend on the selected config, so source does not provide a finite global list. `[src: codex-rs/model-provider-info/src/lib.rs:167-176,200-207,218-224,519-536; codex-rs/model-provider/src/auth.rs:284-309,379-390 @ rust-v0.167.0]`
- `OPENAI_BASE_URL` is context for the OpenAI credential broker when it binds an `OPENAI_API_KEY` to a host. It can change the credential destination, not the selected Codex account. `[src: codex-rs/network-proxy/src/credential_broker/providers/openai.rs:12-32,68-86 @ rust-v0.167.0]`
- The selected Bedrock provider can use `AWS_BEARER_TOKEN_BEDROCK`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY`; AWS SDK auth can also use `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`, and `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`. Bedrock source selection prefers configured command auth, credential export, configured profile, managed credentials, environment bearer token, environment access-key pair, then the AWS SDK chain. Codex explicitly preserves the listed AWS config and token-file variables for its background command; the source delegates the remaining SDK chain and does not enumerate every variable that dependency may read. `[src: codex-rs/model-provider/src/amazon_bedrock/auth.rs:29-90,139-158,185-193; codex-rs/network-proxy/src/aws_sigv4.rs:266-275,293-296,317-336; codex-rs/app-server-daemon/src/background_command.rs:48-76 @ rust-v0.167.0]`
- `GOOGLE_APPLICATION_CREDENTIALS` selects a Google credential file in the default GCP auth path. An explicit provider `credential_file` takes precedence. These provider credentials do not select the Codex account shown by `codex login status`. `[src: codex-rs/model-provider-info/src/lib.rs:183-191; codex-rs/app-server/src/request_processors/account_processor/gcp_setup.rs:157-168 @ rust-v0.167.0]`

The run matrix set each of these 23 fixed variables one at a time: `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `OPENAI_API_KEY`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT`, `CODEX_AUTHAPI_BASE_URL`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE`, `CODEX_REVOKE_TOKEN_URL_OVERRIDE`, `CODEX_APP_SERVER_LOGIN_CLIENT_ID`, `OPENAI_BASE_URL`, `AWS_BEARER_TOKEN_BEDROCK`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`, and `GOOGLE_APPLICATION_CREDENTIALS`. `HOME` and `CODEX_HOME` were bound to the fresh scratch paths in every run, as required to keep the run isolated. The dynamic provider `env_key` and `env_http_headers` variables were not added to the test config because each config was required to contain only the store setting. All 72 calls (baseline plus 23 variables for each of three stores) exited 1. The baseline and most variable cases printed `Not logged in`; the placeholder access token and partial workload identity cases printed errors. No output matched the email pattern or signed-in detector. `[evidence: /Volumes/S1/yooz/remi/artifacts/profiles-epic-2026-11/P1C/r2/placeholder-runs.txt]`

## 2. Default store and `auto`

`AuthCredentialsStoreMode` marks `File` as its default, and configuration resolves an absent setting through that default without an OS-specific branch. The default is therefore `file` on macOS and Linux. On load, `auto` reads keyring first, then reads file if the keyring has no entry or errors. On save, it writes to keyring first and falls back to file on error. Its code path is the same on both platforms, while actual keyring availability was not measured here. `[src: codex-rs/config/src/types.rs:135-148; codex-rs/core/src/config/mod.rs:4582-4590; codex-rs/login/src/auth/storage.rs:593-640 @ rust-v0.167.0]`

## 3. Keyring names and separation

For the CLI auth store, the keyring service is `Codex Auth`; its account is `cli|` plus the first 16 hexadecimal characters of SHA-256 over the canonical `CODEX_HOME` path. Codex's separate secrets namespace uses service `codex` and account `secrets|` plus the same 16-character path hash for the `CodexAuth` namespace. Both produce different account names for distinct canonical homes, so the result is **separated**. Symlink aliases that canonicalize to the same path share an account. `[src: codex-rs/login/src/auth/storage.rs:302-320,343-380; codex-rs/secrets/src/lib.rs:23,182-207 @ rust-v0.167.0]`

## 4. `codex login status` output

- No auth: stderr `Not logged in`, exit 1.
- Stored ChatGPT auth: stderr `Logged in using ChatGPT`, exit 0.
- Stored API-key auth: stderr `API key configured - <formatted key>`, then `Authentication is checked when you send a request.`, exit 0. For a key longer than 13 characters the formatter emits its first 8 and last 5 characters around `***`; shorter values become `***`.

The normal status format strings include no email, account id, or workspace-name fields. The error format `Error checking login status: {err}` interpolates a lower-layer error, so source alone does not establish that every possible error string is free of identifiers. Status explicitly disables `CODEX_API_KEY` environment auth. The logged-in cases above are source characterizations only; no real login was read or created. `[src: codex-rs/cli/src/login.rs:488-553,697-704 @ rust-v0.167.0]`

## 5. App-server control socket path length

The advertised control socket is `$CODEX_HOME/app-server-control/app-server-control.sock`. On Unix, Codex binds the physical socket under the short shared directory `/tmp/codex-daemon-<uid>/<sha256-of-advertised-path>` and leaves a symlink at the advertised path. If connecting to the advertised path fails with `InvalidInput` because it exceeds `sun_path`, the client canonicalizes the symlink and retries the short target. The tagged source test creates two distinct homes under a 120-character parent, starts both sockets, and connects through both long paths. The source states no numeric `CODEX_HOME` maximum; ordinary filesystem path limits still apply. `[src: codex-rs/app-server-transport/src/transport/mod.rs:56-80; codex-rs/app-server-daemon/src/lib.rs:351-359; codex-rs/app-server-transport/src/transport/unix_socket.rs:69-145,353-368; codex-rs/uds/src/lib.rs:166-173; codex-rs/app-server-transport/src/transport/unix_socket_tests.rs:63-104 @ rust-v0.167.0]`

## Consequences for P1B

For the Codex account login, set `CODEX_HOME` to the selected profile and scrub `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `OPENAI_API_KEY`, `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT`, `CODEX_AUTHAPI_BASE_URL`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE`, `CODEX_REVOKE_TOKEN_URL_OVERRIDE`, `CODEX_APP_SERVER_LOGIN_CLIENT_ID`, and `OPENAI_BASE_URL` from the launched Codex environment. `CODEX_API_KEY` is an additional higher-precedence source and must be included. For a selected provider, also scrub or explicitly allow its configured `env_key` and `env_http_headers` variable names, plus the AWS and GCP credential variables listed in section 1; otherwise a profile can still use provider credentials from the caller's environment. Keyring isolation is **separated**, so J11 permits an effective store of `keyring` or `auto` from this account-separation finding.
