# Research A: feasibility of hub control from the sandboxed Mac app (#1805)

Date: 2026-11-17. Base: `origin/develop` at `bbcec7d6` (0.9.1-dev.4); every `path:line` below is at that commit.
Read-only research; nothing was run against a hub, a daemon, `remi`, a simulator or the app.
Apple facts cite the documentation page and carry the date read (2026-11-17, rendered from `developer.apple.com`); a fact I could not read there is marked UNVERIFIED.

## 1. Answer in brief

| Ask | Sandboxed Mac App Store or TestFlight app (today's entitlements) | What changes that |
|---|---|---|
| Monitor a hub started by anything | Yes. Outgoing TCP to the same machine needs only `network.client`, which the app has. The app already connects to `127.0.0.1:18765` as a wire client once paired. | Nothing to add for monitoring. Finding an unpaired hub needs a port probe; see 2.2. |
| Start the hub | No, not by the app itself. A child of a sandboxed app inherits the sandbox; a bundled hub inside the sandbox cannot do its job (it cannot reach `~/.claude`, repositories or `~/.remi`). | A user-installed script run through `NSUserUnixTask` (outside the sandbox, user-supplied), or Developer ID distribution. |
| Create and edit `config.toml` | Not directly. The app has no file entitlement and `~/.remi` is outside its container. | (a) a user-granted file (`user-selected.read-write` plus a bookmark), (b) a hub-side write request over the authenticated wire (new protocol), or (c) Developer ID. |
| Show wake state in the icon | The icon exists. The data does not: no wire message carries keep-awake state at `origin/develop`, and the hub holds no assertion (session daemons do). | ADR 0050 slice 4 (`keep_awake_status`, a `keep_awake` capability); a hub change that this request depends on. |

Recommendation (detail in section 6): do A now, add D narrowly (an `[awake]`-only, daemon-validated write plus a read of the effective values) for the Settings menu, make the start button B through an owner-installed fixed-verb script only if the owner wants "start" inside the App Store build, and treat E as the answer only if the owner wants the app to be a full controller.
Two standing rules must be amended or confirmed by the owner before any build: `packages/native/AGENTS.md:39` and ADR 0051 F8 ("never reads `~/.remi`, never spawns, never signals"); see section 5.

## 2. What the native Mac app is today

### 2.1 Shape, sandbox, distribution

- Targets: `RemiMac` (`packages/native/Mac/`), the embedded `MacPushService` extension, the `RemiKit` package (`packages/native/RemiKit`). No `LSUIElement` key in `Mac/Info.plist:1-45`; the app has a Dock icon and a main window.
- **It already has a menu bar item.** `Mac/RemiMacApp.swift:33-42` declares a `MenuBarExtra` with `.menuBarExtraStyle(.window)` (content `MacLiveNeedsYouMenu`, label `MacMenuBarLabel`). The icon is `RemiMenuBarIcon` (`RemiKit/Sources/RemiUI/MenuBarIcon.swift:4-16`, a template image, two states) fed by `RemiMenuBarStatus` (`RemiKit/Sources/RemiUI/MenuBarStatus.swift:7-30`: `pendingCount`, `identityAvailable`). It knows nothing about hubs or wake state.
- **It already has a Settings scene.** `Mac/RemiMacApp.swift:44-53` shows `MacPreferencesView` (`Mac/MacPreferencesView.swift:36-45`): tabs General (notification permission and preferences), Machines (rename, forget, per machine), Identity. There is no hub-control or config surface.
- **Entitlements** (`Mac/Remi.entitlements:5-21`, the whole file): `app-sandbox`; `network.client`; `application-groups` = `$(DEVELOPMENT_TEAM).live.yooz.remi`; `keychain-access-groups` (app id, `live.yooz.remi.secure-push`); `aps-environment`; `usernotifications.time-sensitive`.
  Absent: `network.server`, any `files.*` entitlement, any `temporary-exception.*`, `files.user-selected.executable`.
  The extension is sandboxed with the app group and the secure-push keychain group (`MacPushService/RemiPush.entitlements:5-15`).
  The project sets `ENABLE_APP_SANDBOX = YES` and the entitlements file (`Remi.xcodeproj/project.pbxproj:641-644`).
- **Standing rule** (`packages/native/AGENTS.md:39`): the Mac app targets the App Store "if the sandbox allows it", is sandboxed with `network.client` only, "never spawns agents, never reads `~/.remi`, never signals a process. Anything that needs the machine ... is a request to the hub". ADR 0051 F8 repeats it (`.context/decisions/0051-account-profiles-in-the-apps.md:62-64`), including that the Mac app on the same machine "is a wire client like any other: loopback is not identity (#873)".
- **Distribution:** TestFlight now (`docs/TESTFLIGHT.md:131-186`: `bun run testflight:macos`, an App Store `.pkg` signed with Mac distribution and installer certificates, owner uploads). Owner decision 2026-10-06 (#1233): "the App Store if the sandbox allows it, otherwise Developer ID" (`.context/native-apps-plan-2026-10.md:113`, `.context/plan.md:156`). So Developer ID is a pre-approved fallback, not a new idea.
- Minimum OS macOS 26, Swift 6, no third-party dependencies without owner approval (`packages/native/AGENTS.md:36-38`).

### 2.2 How it finds and talks to a hub

- A machine is added by hand (Add machine sheet) or by pairing; `AddMachineDraft` defaults to `127.0.0.1` and port `18765` (`RemiKit/Sources/RemiKit/Store/AddMachineDraft.swift:30,34`).
  `packages/native/Mac/MacFirstRunView.swift:11-20` shows "Add your first machine" and says nothing about starting a hub or what to run.
- Bonjour browse (`RemiKit/Sources/RemiKit/Discovery/LocalMachineDiscovery.swift:48`) only re-finds **saved** machines: a result must carry `auth=true`, `role=hub` and a fingerprint that is in the saved targets (`:98-113`). It does not discover a new hub. `Mac/Info.plist:28-33` declares `_remi._tcp` and a local-network usage string.
- The default hub bind is `127.0.0.1` (`packages/daemon/src/config/config.ts:240`) and `AGENTS.md` ("Transport Options") says mDNS does not advertise on a loopback bind. So on a default install Bonjour finds nothing, and "a hub is running on this Mac" is knowable only by connecting to `127.0.0.1:18765` (first free port of 18765 to 18784, `packages/native/AGENTS.md:64`).
- On first connect an unknown key is challenged and stays pending until `remi authorize <fingerprint>` runs at the machine (`packages/native/AGENTS.md:66`; ADR 0037, #873). The app shows `waitingForApproval` (`RemiKit/Sources/RemiKit/Store/MachineStore.swift:133-140`).
  Consequence for "start the hub": a hub the app starts still needs a terminal approval, unless the owner decides the app may approve itself (a security decision; section 5).
- What the app learns from a hub: `hello_ack` (`RemiKit/Sources/RemiKit/Protocol/WireMessages.swift:78-97`: `serverVersion`, `protocolVersion`, `capabilities`, `harnesses`, `machine`), the session list with `daemonPorts`, and `remi_status` (`MachineStore.swift:2901`). The hub also writes `status` data to disk (2.3) but the app does not read it.
- Sandbox consequence for monitoring: connecting to `127.0.0.1` needs `com.apple.security.network.client`, whose documentation says the key allows "a server process running on another machine, or on the same machine" (Apple, `com.apple.security.network.client`, read 2026-11-17). The app already does this; ATS exceptions for loopback are in `Mac/Info.plist:8-27`.
- Presence probe without registering a key: a hub sends `auth_challenge` before the client answers, and a key becomes pending only on `auth_response` (`AuthChallengeMessage`, `WireMessages.swift:99-109`; `AGENTS.md` "Authentication"). Reading the challenge to learn "a hub answers here" is therefore plausible but UNVERIFIED in RemiKit (no pre-auth probe API found; needs a spike).

## 3. How the hub is started, supervised and configured today

### 3.1 Start, stop, status, LaunchAgent

- Hub files: `~/.remi/daemon.pid` and `daemon-status.json` (`packages/daemon/src/cli/daemon-manager.ts:27-28`), log `daemon.log` (`:29`). The hub self-writes the PID file; `remi status` and `stop` fall back to the status file (`docs/agent-reference/hub-mode.md`, "Hub mode").
- `remi start` detaches: it finds a free port, spawns `<remi> serve --port N` with `detached: true` and `child.unref()` (`daemon-manager.ts:196-262`) and polls `daemon-status.json` for up to 5 s; a second start refuses with "Hub already running" (`:202`).
- The hub re-executes its own binary to start session daemons (`resolveRemiCommand`, `daemon-manager.ts:143-170`; `spawnRemiDaemon`, `:598-640`), so any hub needs a runnable `remi` binary and the user's real home, repositories and `~/.claude` (`transcript/transcript-discovery.ts:29`, `cli/statusline-installer.ts:81`).
- `remi --install` writes `~/Library/LaunchAgents/com.yooz.remi.plist` (`cli/service-templates.ts:16-17,40-66`): `<PATH remi> serve`, `RunAtLoad`, `KeepAlive.SuccessfulExit=false` so a clean `remi stop` stays stopped. It refuses under a `REMI_HOME` override (`config/remi-home.ts:64-70`) and bootstraps with `launchctl` (`cli.ts:575-625`).
- Status for a monitor: the hub writes `mode: 'hub'`, `wsPort`, `bind`, `auth` (`cli.ts:3540-3548`); `readHubStatus` is the reader (`daemon-manager.ts:113-141`).
- The `remi` release binary is a `bun build --compile` output (`.github/workflows/release.yml:57`, `package.json:22`) distributed by Homebrew and npm. `release.yml` has no `codesign` or notarization step (grep at this commit); ADR 0050 fact 6 records `/opt/homebrew/bin/remi` as ad hoc signed with no Team ID (`.context/decisions/0050-keep-the-mac-awake.md:32`).

### 3.2 Where config lives and how it is read and written

- Home: `remiHome()` = `REMI_HOME` (absolute) or `~/.remi` (`config/remi-home.ts:48-56`); config path `<home>/config.toml` (`config/config.ts:15-16`).
- Commands: `remi config [show|init|path]` only (`cli/cmd-config.ts:40-63`). `init` creates the file with the commented defaults, `wx` flag, mode `0600` (`config/config.ts:918-933`). **There is no `remi config set`**; a person edits the TOML by hand.
- Loading: once, at process start (`cli.ts:398`). `remi reload` sends SIGUSR1 to live daemons, but the handler only re-validates; "Changes take effect on next daemon restart" (`cli.ts:3704-3714`, `:4125-4133`; `config.ts:808` comment). `docs/agent-reference/keep-awake.md:38`: "Settings apply after a restart."
  So any Settings edit also needs a hub restart to take effect, which the sandboxed app cannot perform today (no stop/restart wire message exists; the request types are listed in `packages/shared/src/protocol.ts`: create, kill, resume, history, notification_host and others, none for config or hub lifecycle).
- Validation is strict and fails closed for the whole CLI: an unknown key in `[awake]` throws `unsupported key(s)` (`config.ts:458-478`), and the docs state that stops every `remi` command at config load (`docs/agent-reference/keep-awake.md:36-38`). A Settings screen that writes a key the installed `remi` does not know breaks that machine's CLI. Version skew between the app and the hub is therefore a real hazard.
- Secrets: `config.toml` can hold `telegram.bot_token` (`config.ts:183-188`, default template `:871`). A file-level read by the app touches a credential even if the screen never shows it; ADR 0049 D10 says remi never "reads, copies, stores, prints or relays a credential or token" (`.context/decisions/0049-account-switching.md:354`, written for harness credentials, same spirit). `[profiles.<id>]` (#1748, ADR 0051 A1) is also planned in this file; it is not in `config.ts` at this commit.
- **No config-read or config-write message exists** at `origin/develop`: `grep` for `config_read|config_write|config_set|config_request` in `packages/shared/src` and `packages/daemon/src` returns nothing. Capabilities today: `workspaces, image_staging, image_insertion, structured_chat, browser_links, file_download, notifications` (`packages/shared/src/protocol-version.ts:35-48`). Adding a message is an ADR 0035 additive capability plus a conformance test with both endpoints constructed.

### 3.3 Keep-awake (#1773) as shipped and as planned

- Shipped (level 1, `docs/agent-reference/keep-awake.md`): each **session daemon** or wrapper runs `caffeinate -i -w <pid>` while it has work; **the hub holds nothing** (`keep-awake.md:12`). Config `[awake]` has five keys: `level1`, `question_hold_minutes`, `idle_grace_seconds`, `stuck_busy_minutes`, `ttl_minutes` (`config.ts:70-81`, validated `:480-499`).
- Not shipped: guard rails (battery floor key `level1_battery_floor_percent`, rejected as an unknown key until its slice), level 2 and every wire surface. ADR 0050 slice 4 is "`keep_awake_status` and start and stop messages ..., a `keep_awake` capability ... a phone start needs `allow_phone = true` set on the Mac" (`.context/decisions/0050-keep-the-mac-awake.md:146`, key table `:150-185`).
- ADR 0050 says level 2 is owned by the hub only (`:92`), uses a sudoers rule the owner installs (`:20`, option A), and that "no agent edits sudoers". The issue text that "the hub reports status" is not true at this commit: `grep -rln awake packages/shared/src` finds nothing, and the status file has no awake field. **The icon's wake states have no data source until slice 4 (or an interim field) ships.**
- The Mac app must never run `sudo` (ADR 0050 constraints; also App Review 2.4.5(v), section 4).

## 5. Constraints and decisions the plan must respect

- **ADR 0030 (relay, not judge) and ADR 0031:** remi never answers a permission without a human choice. Nothing here touches that, but a Mac app that starts and configures the hub must not create an auto-approve path (no key such as an approval policy in the Settings menu).
- **ADR 0035 (versioned capabilities):** a config message or a `keep_awake` surface is an additive capability, listed by the change that ships it; the app decides with `hubSupport`, never by `daemonVersion` (`packages/native/AGENTS.md:57`). Version skew between app and hub on `[awake]` keys is the risk in 3.2.
- **ADR 0038 (decision object):** unaffected; keep-awake state is not a `question`. Do not overload `Question.kind`.
- **ADR 0049 D10:** no reading, storing, printing or relaying a credential or token. `config.toml` may contain `telegram.bot_token`; the app must not hold the whole file in memory or logs. Also: "choose a profile the person did not configure" is never done by remi.
- **ADR 0051 Q1 / A1:** "No app writes profile configuration" because a remote create adds "a configuration-writing surface to the wire", a profile directory is a path, and "a device must not be able to widen what devices can see" (`0051-...md:147-155`), "The Mac app is no exception, even on the same machine (F8)". Relation to #1805: the request is about general and keep-awake configuration, not `[profiles.*]`, so Q1's text does not forbid it. But Q1's reasons (a config-writing wire surface; a device must not widen exposure) apply to any generic write. **Owner decision needed** (one question): does Q1 stand as a profile-only rule, with a narrowly scoped, whitelisted write for `[awake]` and display settings allowed, or does the "no app writes configuration" rule extend to all config? The plan should also state that `[profiles.*]`, `auth`, `daemon.bind`, `daemon.tls`, `network`, `telegram` and `harness` are out of any app write path (a device that could write `auth.enabled = false` or `daemon.bind` would widen exposure; loopback is not identity, so the hub cannot tell the Mac app from a paired phone).
- **ADR 0050 (keep awake):** level 1 is per session daemon and shipped; guard rails and level 2 are planned; the hub owns level 2; every tunable is a key of `[awake]`, keys land with the slice that uses them; no agent edits sudoers; the Mac app never runs `sudo` (also App Review 2.4.5(v)); the phone toggles level 2 only after the owner enables it on the Mac (`allow_phone`). The Settings menu may show and edit only keys the connected hub reports as supported; a key shown for a slice not shipped is exactly the "a key never exists without behavior" violation.
- **`packages/native/AGENTS.md:39`:** the Mac app "never spawns agents, never reads `~/.remi`, never signals a process". Any option that starts the hub, reads the status file or writes the file amends this rule. It is an owner-level rule (#1233) and needs an explicit decision; it should be amended in the same change as the code, with a test that pins it (ADR 0011: do not describe protection the code does not have).
- **`packages/native/AGENTS.md:104,114`:** development and verification use a throwaway `REMI_HOME` and ports 18790 and up, never the owner's hub; the simulator hazard (a pending authorization request on the real hub) applies to any "probe 18765" feature, which must be off or redirected in Debug and simulator builds.
- **Hub-start side effects to design for:** a started hub needs the terminal approval for the app's key (3.2 and 2.2); the LaunchAgent restarts only on crash (`SuccessfulExit=false`), so "start" and "keep running" are different asks; `--install` and a `REMI_HOME` override are mutually exclusive (`remi-home.ts:64-70`).

## 6. Options matrix

| Fits #1233 | yes | yes, if review accepts | no | yes, subject to the Q1 decision | yes, the stated fallback |

Two further paths the matrix excludes on purpose:
- F: the app edits `config.toml` itself through a user-picked file (`files.user-selected.read-write` plus a security-scoped bookmark; no temporary exception). It is App Review friendly, but the app then reads `config.toml` (possible `telegram.bot_token`), must carry its own TOML editor that preserves comments and `[profiles.*]` (no third-party parser allowed without approval), duplicates the daemon's validation, and in-place writes only work for the picked file. I recommend against it for the reasons in D's "security" cell.
- G: a temporary exception for `/.remi/`. Likely rejected (section 4) and it grants the keys and tokens in the folder. Not recommended.

### Recommendation

1. **Now, no owner decision needed: A.** In the existing Mac app, a "This Mac" hub card (reachability of `127.0.0.1:18765`, hub version, paired or waiting for approval) and a first-run empty state that shows the exact commands. Add a presence probe that reads `auth_challenge` only if a spike confirms it registers no key. Off in Debug and simulator builds.
2. **For the Settings menu: D, narrowly.** A `config` capability (ADR 0035) with two messages: read the effective `[awake]` values and the keys this hub supports; write a whitelisted set of keys through the daemon's own validator, atomically, returning "applied after restart". Leave `[profiles.*]`, `auth`, `daemon`, `network`, `telegram`, `harness` out. This keeps the app out of `~/.remi`, keeps D10 intact (the app never touches the token), uses the daemon as the single validator (no Swift copy of the ranges), and reuses the authenticated connection the app already has. It needs the Q1 clarification above and an ADR (next free number) before code. It cannot create the file for a machine with no hub, and applies only after a restart; both must be stated in the UI.
3. **Start:** the owner picks between (i) A only (the app shows `remi start`; the LaunchAgent from `remi --install` is the supported way to keep it running) and (ii) B with a fixed-verb script the user saves into the Application Scripts folder (small, reversible, App Store-compatible by Apple's documented mechanism, review risk medium). I recommend (i) first and (ii) only if (i) proves too thin in the owner's daily use. C is not feasible as a useful hub inside the sandbox.
4. **E** is the right answer only if the owner wants the Mac app to be a full controller (start, stop, restart, edit anything, run `remi authorize`). Choose it deliberately, as a separate decision, because it also changes testing (no TestFlight), updating and the security posture.
5. **The icon (ask 3)** depends on the hub, not the app: ADR 0050 slice 4 or an interim `keep_awake` field on `remi_status` must land first, and level 1 state must be aggregated from the session daemons (the hub holds nothing). Plan this as a daemon task before the icon task.

## 7. What I could not verify

- Whether `Process` can launch `/opt/homebrew/bin/remi` from the sandbox with or without `user-selected.executable`; not run (rule: no launches). A spike in a throwaway sandboxed target against a throwaway `REMI_HOME` would settle it.
- Whether a process started through `NSUserUnixTask` and detached survives the app quitting, and whether `launchctl kickstart` of the `com.yooz.remi` LaunchAgent works from the user script (it should; unproven). Whether a sandboxed app may call `launchctl` itself: not established.
- Whether TestFlight for Mac applies the same temporary-exception policy as the Mac App Store (the DTS engineer did not know).
- Whether a registered `SMAppService` agent with an unsandboxed executable fails App Store validation. The ecosystem note says validation error 90296 applies to a nested unsandboxed helper `.app`; I did not re-read Apple's validation text.
- Whether a bun-compiled `remi` signed with only `app-sandbox` plus `inherit` (no hardened runtime) runs, or is accepted by App Store validation, and whether Developer ID notarization of the bun binary succeeds (Bun issue 7208 reports strict-validation failures with `--deep`; the exact Bun entitlement plist was not read in full).
- Whether the app's push, app group and keychain entitlements are available under a Developer ID provisioning profile (option E).
- Whether `auth_challenge` alone can serve as a no-side-effect presence probe in RemiKit.
- Hardware and macOS-version behavior of keep-awake level 2 (ADR 0050 already marks most of it UNVERIFIED; nothing was checked on a MacBook).
- The exact written wording of Apple's Mac App Store review of temporary exceptions: the only source I found is DTS forum opinion.
