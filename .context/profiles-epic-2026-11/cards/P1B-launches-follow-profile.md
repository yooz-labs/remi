## Goal

A local wrapper session (`remi`, `remi new`, `remi claude`, `remi codex`), a hub child (`remi --daemon`) and every resume route run their agent under the profile the resolver picks, with a complete scrubbed environment, a refusal before anything is spawned when the profile's sign-in is not its own, the profile recorded with the session, and resume refusing a removed, changed or conflicting profile; with no `[profiles]` table every launch is byte-for-byte what it was; a remote launch cannot carry a profile yet and says so.

## Decided design

Settled (every rule the worker needs is here; nothing below is left to a later reading of the P1C note):

1. **Pin first.** Keep the existing local commit `764826fe` (pin tests of the unmodified launch paths). They must keep passing with no `[profiles]` table.
2. **Selection.** `--remi-profile <id>` is a remi flag accepted anywhere before `--` by every session-starting form (`remi`, `remi new`, `remi claude`, `remi codex`, `remi --daemon`, `--resume`, `remi new --recent`) and is never passed to the harness; `REMI_PROFILE` is read once at boot. Resolution uses `resolveProfile` once per session start, in the process that spawns the agent, with the session's working directory (after `--dir`, or after the `--recent` picker's change of directory). `remi new --recent` is a new session: it resolves like any new session and reads no stored record. The built-in `default` (whatever its source) takes today's code path unchanged: no environment replacement, no check, no new record fields; a `warning` from `resolveProfile` is printed to stderr and the daemon log before the spawn.
   **Remote launches (`--host`).** The wire has no profile field until P2B. An explicit `--remi-profile` naming anything but `default` on a `--host` launch is refused before any connection, exit code 2: `Choosing a profile for a session on another machine is not supported yet. That machine's folder mapping or default profile applies; run the command without --remi-profile.` With `--host` and a non-empty local `REMI_PROFILE` other than `default`, print once `REMI_PROFILE applies to this machine only; the remote machine chooses by its own folder mapping or default.` and continue.
3. **A configured profile's launch**, in this order; any refusal spawns nothing and prints its text (backticked texts are literal; `<id>`, `<harness>`, `<source>`, `<reason>`, `<value>`, `<name>` are filled in):
   0. A `resolveProfile` error is refused with the error text.
   a. Harness: an explicit `--harness` or `remi codex`/`remi claude`, else the profile's `harness`, else `[harness] default`; a harness the profile does not configure: `Profile <id> does not configure <harness>.` An `expects` other than `subscription` or `api_key`: `Profile <id> expects <value>, which this build does not support.`
   b. **Environment.** `profileEnvironment(...)` with `PROFILE_CREDENTIAL_ENV` extended to exactly P1A's 42 names plus the following, and the guard test's hard-coded list updated to match:
      - from Claude Code's environment-variable reference (code.claude.com/docs/en/env-vars, read by the lead on 2026-11-17): `ANTHROPIC_AWS_WORKSPACE_ID`, `ANTHROPIC_GOOGLE_CLOUD_WORKSPACE_ID`, `ANTHROPIC_GOOGLE_CLOUD_PROJECT`, `ANTHROPIC_VERTEX_PROJECT_ID`, `ANTHROPIC_FOUNDRY_RESOURCE`, `ANTHROPIC_AWS_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `ANTHROPIC_BEDROCK_MANTLE_BASE_URL`, `ANTHROPIC_FOUNDRY_BASE_URL`, `ANTHROPIC_GOOGLE_CLOUD_BASE_URL`, `ANTHROPIC_VERTEX_BASE_URL`, `CLAUDE_CODE_SKIP_ANTHROPIC_AWS_AUTH`, `CLAUDE_CODE_SKIP_ANTHROPIC_GOOGLE_CLOUD_AUTH`, `CLAUDE_CODE_SKIP_BEDROCK_AUTH`, `CLAUDE_CODE_SKIP_FOUNDRY_AUTH`, `CLAUDE_CODE_SKIP_MANTLE_AUTH`, `CLAUDE_CODE_SKIP_VERTEX_AUTH`;
      - every one of the P1C note's 23 fixed names not already present: `OPENAI_FEDERATION_RULE_ID`, `OPENAI_IDENTITY_TOKEN_FILE`, `OPENAI_WORKLOAD_IDENTITY_CONTEXT`, `CODEX_AUTHAPI_BASE_URL`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE`, `CODEX_REVOKE_TOKEN_URL_OVERRIDE`, `CODEX_APP_SERVER_LOGIN_CLIENT_ID`, `OPENAI_BASE_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`, `GOOGLE_APPLICATION_CREDENTIALS`.

      **Policy for general cloud variables (lead, 2026-11-17; this replaces the earlier "not scrubbed" sentence):** the owner's rule is that the list errs wide and that a profile launch must not inherit another account's identity, so the AWS and Google names above are removed from the inherited environment of **every** configured-profile launch, Claude and Codex alike. Because they are in `PROFILE_CREDENTIAL_ENV`, P1A's loader already refuses them in a profile's `env` ("not supported in this build"); keep that. Consequence, recorded as a known limit in the agent reference and the PR body: a profile session has no exported AWS or Google identity; the agent's own cloud commands fall back to their tools' file-based defaults (for example `~/.aws/config`, `~/.aws/credentials`, gcloud's application-default credentials), which remi neither reads nor changes, and a Codex profile that selects a cloud provider configures that provider's identity in its own `CODEX_HOME/config.toml`. Whether a profile's `env` may later carry cloud pointers (`AWS_PROFILE` and the like) is owner call J20; P1B does not wait for it. P1A's own tests use `AWS_PROFILE` as a valid `env` key (`packages/daemon/tests/profiles/model.test.ts:32, 43, 55`; `commands.test.ts:95, 110` on `884dcf80`): change those fixtures to a plain non-credential name (for example `MY_TOOL_MODE`) and add one test that `AWS_PROFILE` in a profile's `env` is now refused; this is expected, not a stop.

      **Dynamic Codex provider names (P1C "Selected model-provider credentials"):** for a profile that configures Codex, read its `CODEX_HOME/config.toml` if it exists, parse it with `smol-toml`, and collect only names: each string value of `model_providers.<id>.env_key` and each string value inside `model_providers.<id>.env_http_headers`; never read or keep any variable's value. Delete each collected name from the launch environment (and from the environment `checkLogin` uses), after `profileEnvironment`. A profile `env` that sets one of those names is refused: `Profile <id> sets <name>, which its Codex configuration reads as a credential; remi does not store credentials.` A `config.toml` that exists but does not parse: `Could not read the Codex configuration of profile <id> (config.toml).`

      **Recheck before the PR:** run `LC_ALL=C grep -a -o -E 'CLAUDE_CODE_USE_[A-Z_]+|ANTHROPIC_[A-Z_]*(KEY|TOKEN|SECRET|CREDENTIAL|HEADERS|SCOPE|ID|CONFIG_DIR|PROFILE|PROJECT|RESOURCE|BASE_URL)[A-Z_]*|CLAUDE_CODE_[A-Z_]*(OAUTH|TOKEN_FILE_DESCRIPTOR|API_KEY|CLIENT_CERT|CLIENT_KEY|GATEWAY_TOKEN|ACCESS_TOKEN|SKIP_[A-Z_]*_AUTH)[A-Z_]*' "$(readlink "$HOME/.local/bin/claude")" | sort -u` (names only) and compare with the list: a name it finds that is not on the list and whose name says it selects a provider, a credential, an account or an auth endpoint is added and listed in the PR; a name that is plainly a feature or limit switch (for example `CLAUDE_CODE_USE_POWERSHELL_TOOL`, `CLAUDE_CODE_MAX_OUTPUT_TOKENS`) is not; an unclear name is added (the list errs wide) and listed under "added as unclear" in the PR. If the binary cannot be read, use the documentation page; if neither, stop.
   b2. Shared stores: P1A refuses shared directories and the built-in default's directories; P1B adds one launch-level test that such a configuration starts nothing.
   b3. **P1A escape, fixed here (risk R18).** `profile-config.ts:163-174` compares `path.resolve` results. Compare canonical forms instead, for comparison only: `fs.realpathSync.native` of the longest existing ancestor joined with the remaining segments, applied to every configured directory and to `$HOME/.claude` and `$HOME/.codex`. The stored and launched path stays the configured `path.resolve`d one (Claude Code keys its keychain entry on the exact directory string). Error texts stay P1A's.
   c. **Codex store (P1C: separated).** The merged note says keychain entries are separated per canonical `CODEX_HOME` and the default store is `file`. Remove P1A's `file`-only gate: `checkLogin` no longer calls `codexUsesFileStore` (it runs `codex login status` under the profile environment whatever the store), `remi profile login --harness codex` no longer refuses a non-`file` home, and the unused `codexUsesFileStore` and its keychain refusal text are deleted with their tests updated. No store-based refusal remains.
   d. **Check.** `checkLogin` under the exact launch environment (after b's deletions) and directory; anything but `signed_in` is refused: `signed_out`, `Profile <id> is not signed in to <harness>. Run: remi profile login <id> --harness <harness>`; `not_own_login`, `This profile's login is not what will be used (<source>).`; `unknown`, `Could not confirm the sign-in of profile <id> (<reason>). Run: remi profile ls`.
   e. **Warnings.** P1A's configuration-level warnings are printed to stderr and the daemon log before the spawn, names only.
   f. **Arguments.** The profile's `args` follow remi's own arguments; for Codex they pass the same validation as user arguments after `--` (`harness/codex/codex-args.ts`), whose refusals stay.
   g. **Spawn.** `PTYSession` gains an option to use the given environment as complete (no `process.env` merge; `FORCE_COLOR`, `TERM` and `withoutRemiSecrets` still applied); `buildClaudeChildEnv`'s values are laid over the profile environment; the built-in path keeps today's merge exactly.
   h. **Claude transcripts.** The session daemon's `TranscriptDiscovery` and `ClaudeHarness.transcriptPath` use `<claude dir>/projects` for a Claude profile session (resolve before `cli.ts:1186` builds the discovery, or build it after resolution).
   i. **Codex.** `CodexLaunchDeps.env` returns the launch environment, so socket resolution, the app-server client, `preflight` and the TUI's `childEnv` use the profile's `CODEX_HOME`.
   j. **Download protection.** For a profile session `cli.ts` passes the profile's Claude directory and Codex home as `claudeConfigDirectory` and `codexHome`.
4. **Record and sidecar.** Before the spawn, at the point the binding is written today, the record gains optional `profile` and `profileSnapshot` (`{revision, claudeDir?, codexDir?, claudeExpects?, codexExpects?}`), round-tripped like `harness`; a new sidecar `<remiHome()>/session-profiles.json` (`{version: 1, sessions: {<remi session id>: {profile, revision}}}`, mode 0600, pruned with the records) records the same id and revision, every read-modify-write under `withInterprocessFileLock` with a per-writer temporary file (`${path}.${process.pid}.tmp`) renamed into place. The agent reference says the sidecar narrows and does not close the older-remi hazard (an older binary that resumes by itself never reads it). Nothing about profiles goes on the wire.
5. **Resume routes:** bare `--resume` (the most recent Claude session overall, as today; its record's profile then applies), `--resume <id or prefix>`, a hub `resume_session_request` (a child with `--resume <id>`), and `remi codex resume <thread id>` when a stored Codex record names that thread. For a Codex record with a profile, `codexResumeCommand` prints `cd <dir> && remi codex --remi-profile <id> resume <thread>` (each variable word shell-quoted). Each route reads the record and the sidecar; each refusal spawns nothing and names only the id:
   - neither has a profile: the built-in `default`, today's behavior;
   - the sidecar names a profile and the record does not, the record names one and the sidecar has no entry, or they differ: `This session's profile information was changed by another remi process. Start a new session.`;
   - the profile is no longer configured: `This session was started in profile <id>, which no longer exists. Start a new session.`;
   - its current revision differs from the snapshot's: `Profile <id> changed after this session started. Start a new session.`;
   - `--remi-profile` or `REMI_PROFILE` names a different profile: `This session belongs to profile <id>. Resume it without --remi-profile, or with --remi-profile <id>.`;
   - otherwise the resume runs under that profile with item 3's checks.
6. **Hub children.** A child inherits the hub's environment and resolves its own profile: the hub process's `REMI_PROFILE` (if the hub was started with one), else the requested directory's folder mapping, else the machine default, else the built-in `default`. No client sends `create_session_request.profile` before a daemon lists `session_profiles` (ADR 0035; P2B adds both), so P1B handles no such field. An omitted wire `harness` stays `--harness claude` (ADR 0033), which the child treats as explicit; a profile's own `harness` default applies only to a local launch without `--harness`, `remi codex` or `remi claude`; a hub child whose profile does not configure Claude is refused by item 3a. A refused child exits with code 78 after logging its reason; `spawnRemiDaemon` attaches `child.once('exit', ...)` before `child.unref()` and its poll checks the recorded code first; exit code 78 becomes the client-visible error "The session's profile could not start. Run remi profile ls on the machine." (no path); every other early exit keeps today's message.
7. **Documentation in the repository:** `docs/agent-reference/profiles.md` gains what this slice ships, the refusal texts, the sidecar and resume rules, the cloud-variable known limit of item 3b, the remote-launch refusal, and what is still missing until phase 2 (the profile on session-list entries, remote selection and visibility, the hub's multi-profile transcript discovery, the status line in profile sessions, download protection of inactive profiles).
The implementer may choose: names; where in `cli.ts` resolution sits (before any harness or discovery is built); the shape of the complete-environment option; how tests simulate an older writer; test names and files.

Never do: run the real `claude` or `codex` in a session; read a credential or any environment value of a credential name; write the owner's `~/.remi`, `~/.claude*`, `~/.codex*` or `~/.aws`; bind ports 18765 to 18769.
