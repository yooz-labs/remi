## Goal

A wrapper session (`remi`, `remi codex`), a hub child (`remi --daemon`) and a resume each run their agent under the profile the resolver picks, with a complete scrubbed environment, a refusal before anything is spawned when the profile's sign-in is not its own, the profile recorded with the session, and resume refusing a removed, changed or conflicting profile; with no `[profiles]` table every launch is byte-for-byte what it was.

## Decided design

Settled:

1. **Pin first.** The first commit adds tests that record, on the unmodified source, the argv and environment the agent sees for: a wrapper Claude session, a `--daemon` Claude session (extend `launch-characterization.test.ts`), and a hub-created Codex session with the fake `codex` and the stand-in app-server (extend `hub-create-session.test.ts`). The environment is recorded as the presence and value of `CLAUDE_CONFIG_DIR` and `CODEX_HOME` and the names (never values) of every variable in `PROFILE_CREDENTIAL_ENV`, with the daemon's own environment setting all of them to planted values. These tests must pass before and after the change with no `[profiles]` table.
2. **Selection.** `--remi-profile <id>` is accepted by every session-starting form (`remi`, `remi new`, `remi claude`, `remi codex`, `remi --daemon`, `--resume`, and `remi new --recent`) and is never passed to the harness; `REMI_PROFILE` is read once at boot. Resolution runs once per session start, in the process that spawns the agent, with the session's working directory (after `--dir`, or after the `--recent` picker's change of directory), using P1A's resolver. `--recent` is not a resume route (verified on `origin/develop` `884dcf80`, `cli.ts:1045-1071`): `remi new --recent` lets the person pick a recent directory for a **new** session, so it resolves the profile like any new session, from the flag, `REMI_PROFILE`, the picked directory's folder mapping or the machine default; it reads no stored session's profile.
   **Remote launches (`--host`).** The wire carries no profile until phase 2 (#1749, P2B adds `create_session_request.profile` behind `session_profiles`; ADR 0049 D6), so P1B changes no message: `remi new --host HOST` (or any `--host` launch) with an explicit `--remi-profile` naming anything but `default` is refused before any connection, with `Choosing a profile for a session on another machine is not supported yet. That machine's folder mapping or default profile applies; run the command without --remi-profile.` and exit code 2; a `REMI_PROFILE` in the local environment does not reach the remote machine, so with `--host` and a non-empty `REMI_PROFILE` other than `default` the CLI prints `REMI_PROFILE applies to this machine only; the remote machine chooses by its own folder mapping or default.` once and continues. The remote child then resolves its profile as design item 6 says. The built-in `default` takes today's code path unchanged: no environment replacement, no check, no new record fields.
3. **A configured profile's launch.** In this order, and any refusal spawns nothing:
   Message templates below are in backticks; `<id>`, `<harness>`, `<source>` and `<reason>` are filled in by the code.
   0. Configuration: with a `[profiles]` table P1A reported as unusable (owner call J14), P1A's resolver (its design item 8a) decides: an explicit, raw-folder or raw-machine-default selection is refused with the error and nothing is spawned; any other plain launch takes the built-in `default` and P1B prints the resolver's one-line warning to stderr and the daemon log before the spawn (a hub child's warning reaches the hub log). An `expects` this build does not check (J15) is refused: `Profile <id> expects <value>, which this build does not support.`
   a. Harness: an explicit `--harness` or `remi codex`/`remi claude`, else the profile's `harness`, else `[harness] default`; a harness the profile does not configure is refused: `Profile <id> does not configure <harness>.`
   b. Environment: P1A's builder (the configured `CLAUDE_CONFIG_DIR` and `CODEX_HOME` are set after the profile's `env`, and P1A's loader refuses those names, `HOME` and `XDG_CONFIG_HOME` in `env`), with `PROFILE_CREDENTIAL_ENV` as P1A's design item 8d lists it, plus every further Codex name P1C's note lists, plus these names from Claude Code's environment-variable reference (code.claude.com/docs/en/env-vars, read by the lead on 2026-11-17), which select or route a provider sign-in and so err wide as the owner's rule asks: `ANTHROPIC_AWS_WORKSPACE_ID`, `ANTHROPIC_GOOGLE_CLOUD_WORKSPACE_ID`, `ANTHROPIC_GOOGLE_CLOUD_PROJECT`, `ANTHROPIC_VERTEX_PROJECT_ID`, `ANTHROPIC_FOUNDRY_RESOURCE`, `ANTHROPIC_AWS_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `ANTHROPIC_BEDROCK_MANTLE_BASE_URL`, `ANTHROPIC_FOUNDRY_BASE_URL`, `ANTHROPIC_GOOGLE_CLOUD_BASE_URL`, `ANTHROPIC_VERTEX_BASE_URL`, `CLAUDE_CODE_SKIP_ANTHROPIC_AWS_AUTH`, `CLAUDE_CODE_SKIP_ANTHROPIC_GOOGLE_CLOUD_AUTH`, `CLAUDE_CODE_SKIP_BEDROCK_AUTH`, `CLAUDE_CODE_SKIP_FOUNDRY_AUTH`, `CLAUDE_CODE_SKIP_MANTLE_AUTH`, `CLAUDE_CODE_SKIP_VERTEX_AUTH`; each is also refused in profile `env` ("not supported in this build") and added to the guard test's hard-coded list. General cloud tooling variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_PROFILE`, `GOOGLE_APPLICATION_CREDENTIALS` and the like) are not scrubbed: the agent's own commands may need them, and they reach Claude Code's providers only through a provider selector, which is scrubbed. Because the CLIs update themselves, P1B rechecks the Claude names on the installed version with the lead's method: `LC_ALL=C grep -a -o -E 'CLAUDE_CODE_USE_[A-Z_]+|ANTHROPIC_[A-Z_]*(KEY|TOKEN|SECRET|CREDENTIAL|HEADERS|SCOPE|ID|CONFIG_DIR|PROFILE)[A-Z_]*|CLAUDE_CODE_[A-Z_]*(OAUTH|TOKEN_FILE_DESCRIPTOR|API_KEY|CLIENT_CERT|CLIENT_KEY|GATEWAY_TOKEN|ACCESS_TOKEN)[A-Z_]*' "$(readlink "$HOME/.local/bin/claude")" | sort -u` (names only, never values), and the "Authentication" and provider sections of code.claude.com/docs/en/env-vars; any new sign-in or provider-selector name is added and listed in the PR; if neither source can be read, stop and report.
   b2. Shared stores (P1C: keychain entries and `auth.json` follow the canonical directory): P1A enforces directory uniqueness and refuses the built-in default's directories (P1A design item 8c); P1B adds one launch-level test that such a configuration starts nothing.
   b3. **P1A escape, fixed here.** On `origin/develop` `884dcf80`, P1A's uniqueness check and its built-in-default comparison (`profiles/profile-config.ts:163-174`) compare `path.resolve` results, which handle `~/` expansion, `..` and trailing slashes but not symlink aliases or a case-insensitive file system, although P1A design item 8c says "after canonicalization". P1B canonicalizes for comparison only: the canonical form of a directory is `fs.realpathSync.native` of its longest existing ancestor joined with the remaining path segments (so a default directory not yet created under a symlinked remi home is covered), and `$HOME/.claude` and `$HOME/.codex` are canonicalized the same way; the configured, `path.resolve`d path stays what is stored and what `CLAUDE_CONFIG_DIR` and `CODEX_HOME` are set to, because Claude Code keys its keychain entry on the exact directory string (#1157 gotcha). The error texts stay P1A's.
   c. Codex store: if P1C's answer for keyring is "not separated" or "not settled", a Codex launch is refused when the effective `cli_auth_credentials_store` (the key in `<CODEX_HOME>/config.toml`, else the default P1C found) is `keyring` or `auto`: `Profile <id> keeps its Codex sign-in in the system keychain, which Codex does not keep apart per profile. Add this line to <CODEX_HOME>/config.toml and sign in again: cli_auth_credentials_store = "file"` (this is the person's own terminal, so the local path is shown). If P1C says "separated", no refusal, and P1B also removes P1A's `file`-only gate on `remi profile login --harness codex` and on the Codex check (P1A design items 4 and 6), with a test that a keyring store then proceeds; otherwise P1A's gate stays.
   d. Check: P1A's `checkLogin` under the exact launch environment and directory; anything but `signed_in` is refused with: for `signed_out`, `Profile <id> is not signed in to <harness>. Run: remi profile login <id> --harness <harness>`; for `not_own_login`, `This profile's login is not what will be used (<source>).` (including source `configDirectory`, when the status names a configuration directory other than the profile's: pack review D8); for `unknown`, `Could not confirm the sign-in of profile <id> (<reason>). Run: remi profile ls`.
   e. Warnings: P1A's configuration-level warnings are printed to stderr and the daemon log before the spawn, names only.
   f. Arguments: the profile's `args` are appended after remi's own arguments; for Codex they pass the same validation as user arguments after `--` (`harness/codex/codex-args.ts`), so its refusals (`-p/--profile`, `-c`, ...) stay.
   g. Spawn: `PTYSession` gains an option to use the given environment as complete (no `process.env` merge; `FORCE_COLOR`, `TERM` and `withoutRemiSecrets` still applied); the Claude launch's `buildClaudeChildEnv` values are laid over the profile environment; the built-in path keeps the merge exactly as today.
   h. Claude: the session daemon's `TranscriptDiscovery` and `ClaudeHarness.transcriptPath` use `<claude dir>/projects` for a Claude profile session (resolve the profile before `cli.ts:1171` builds the discovery, or build it after resolution); the status line is not installed into the profile's settings in this slice (P2A).
   i. Codex: `CodexLaunchDeps.env` returns the launch environment, so the socket resolution, the app-server client, `preflight` and the TUI's `childEnv` all use the profile's `CODEX_HOME`.
   j. Download protection: for a profile session, `cli.ts` passes the profile's Claude directory and Codex home as `claudeConfigDirectory` and `codexHome` instead of the process environment's values.
4. **Record and sidecar.** Before the spawn, at the point the binding is written today, the session record gains `profile` (the id) and `profileSnapshot` (`{revision, claudeDir?, codexDir?, claudeExpects?, codexExpects?}`), both optional and round-tripped as plain values like `harness`; and a new sidecar `<remiHome()>/session-profiles.json` (`{version: 1, sessions: {<remi session id>: {profile, revision}}}`, mode 0600, pruned with the records) records the same id and revision. The sidecar uses the same concurrency pattern as `session/session-store.ts`: every read-modify-write runs under `withInterprocessFileLock` on the sidecar's path, and writes go to a per-writer temporary file (`${path}.${process.pid}.tmp`) that is renamed into place (pack review D12). An older remi that rewrites `sessions.json` does not know the sidecar, so a lost record field is detected at resume (owner call J9; if the owner chooses otherwise, the lead changes this item before dispatch). This narrows the older-remi hazard and does not close it: an older remi binary that resumes a session itself never reads the sidecar, and the agent reference says so, as `session/legacy-writers.ts` does for Codex. Neither file's profile data is ever sent on the wire in this slice.
5. **Resume.** The resume routes, verified on `origin/develop` `884dcf80`: bare `--resume` (the most recent Claude session, `SessionStore.getMostRecent('claude')`, `cli.ts:921-928`; it keeps choosing the most recent session overall, and that record's profile then applies), `--resume <id or unique prefix>` (`cli.ts:929` onward), a hub `resume_session_request` (the hub starts a child with `--resume <id>` through `startSession`), and `remi codex resume <thread id>` (the command `remi --sessions` prints through `codexResumeCommand`, `harness/codex/codex-session.ts:172`; when a stored Codex record names that thread, its profile applies by the rules below, and for such a record the printed line adds the profile flag in a form `remi codex` accepts, tested by parsing the printed line). Each route reads the record and the sidecar; each refusal spawns nothing and names only the id:
   - neither has a profile: the built-in `default`, today's behavior;
   - the sidecar names a profile and the record does not, the record names a profile and the sidecar has no entry for the session, or they differ: `This session's profile information was changed by another remi process. Start a new session.`;
   - the profile is no longer configured: `This session was started in profile <id>, which no longer exists. Start a new session.`;
   - its current revision differs from the snapshot's: `Profile <id> changed after this session started. Start a new session.`;
   - `--remi-profile` or `REMI_PROFILE` names a different profile: `This session belongs to profile <id>. Resume it without --remi-profile, or with --remi-profile <id>.`;
   - otherwise the resume runs under that profile, with item 3's checks.
6. **Hub.** Children inherit the hub's environment as today and resolve their own profile from it: an inherited `REMI_PROFILE` of the hub process (a choice made when the hub was started), else the requested directory's folder mapping, else the machine default, else the built-in `default`. There is no protocol field in this slice: by ADR 0035 no client sends `create_session_request.profile` before a daemon lists `session_profiles` (P2B adds both), so P1B adds no handling for it. **Omitted harness:** the hub keeps turning an omitted wire `harness` into `--harness claude` (`checkHarnessRequest`, `cli/handlers/create-session-events.ts:146-189`; ADR 0033: absence means Claude), and the child treats it as an explicit harness; so a profile's own `harness` default applies only to a local launch with no `--harness` and no `remi codex`/`remi claude` (design item 3a), and a hub child whose folder-mapped profile does not configure Claude is refused with item 3a's text, nothing spawned. A child refused by item 3 or 5 exits with code 78 after logging its reason. Today the hub learns of an early exit only through `process.kill(pid, 0)` in `spawnRemiDaemon`'s registration poll (`cli/daemon-manager.ts:660-680`), which carries no exit code, so P1B attaches `child.once('exit', (code) => ...)` before `child.unref()` and has the poll check that recorded code first (pack review E25, D25); the hub maps exit code 78 to the client-visible error "The session's profile could not start. Run remi profile ls on the machine." (no path), and keeps today's message for every other early exit.
7. **Documentation in the repository:** `docs/agent-reference/profiles.md` gains what this slice ships, the refusal texts, the sidecar and resume rules, and what is still missing until phase 2 (the profile on session-list entries and remote visibility, the hub's multi-profile transcript discovery, the status line in profile sessions, download protection of inactive profiles).
The implementer may choose: names, where in `cli.ts` resolution sits (before any harness or discovery is built), the shape of the complete-environment option, test names.

Never do: run the real `claude` or `codex` in a session; read a credential; write the owner's `~/.remi`, `~/.claude*` or `~/.codex*`; bind ports 18765 to 18769.
